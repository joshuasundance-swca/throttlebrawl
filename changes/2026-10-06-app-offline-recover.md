A tab left open across an update now catches up with it, and never in the middle of a race. Before, only a missing piece of game code sent the tab to the new version; a region's maps, the models and the scenery kits just went missing, so San Francisco could show no routes at all. Now any missing file of the old version sends the tab to the current one, once, when it loses nothing: straight away in the menus, and after the race otherwise. A race finishes on what it has already loaded; if the update arrived while you raced, the result screen says so and offers "Reload now", and the result stays on screen until you leave it. If an update interrupts the game while it saves itself for offline play, the tab reloads to the new version and saves that one whole, so an offline launch opens it.

For devs: `[default]`, not phone-verified, no local browser run (CI runs `tests/e2e/app-offline.spec.ts`). Playtest 4 run A fix batch's live check: new mustFix 2 (a and b) and punch item 1; the details are in `docs/engineering.md`, Deploy, Offline.
- **Three signs of a deploy** (`recoverStaleBuild` in the new `src/platform/stale-build.ts`): a lazy chunk that fails (`vite:preloadError`, as #584), any fetch of a file under `assets/` that answers 404 or 410 (`watchFetches` in `src/platform/index.ts` wraps the page's `fetch` once and passes every answer on untouched, so content/'s map and pack data, assets/' models and kits and audio/'s voices are all heard), and a worker install that fails (`watchInstall`: the installing worker turns redundant before it installed).
- **Ask the host first**: a sign alone never reloads. The page fetches `sw.js` (`cache: 'no-store'`), whose cache name names the build the host serves (`hostBuildOf`); only another build counts. So a missing file that is not a deploy, or an install that failed on a dropped connection, reloads nothing. Four 404s at once ask once.
- **Never mid-race**: app/ answers "does a reload lose nothing now" with `reloadLosesNothing` (`src/app/states.ts`: the menus, the start screen and boot; not a race, not a result). A deploy found mid-race waits; `go` calls `settle` after each change of screen, after the tap's own steps (Restart and Race again pass through the menu and stay in the race). On the result screen `ui.offerReload` shows the card with "Reload now".
- **#584's guarantees kept**: the install is still all or nothing with one build per cache (the worker is unchanged); one reload per build (the same session key); never a loop; never offline; never without session storage.
- **Tests, with a simulated deploy**: `src/platform/stale-build.test.ts` (a static host serving one build at a time, its `sw.js` naming it). Against #584's behaviour behind the same interface, 10 of its 12 cases failed: 0 reloads after San Francisco's 4 map files answered 404, 0 after a failed install, and a reload mid-race on a stale chunk. `src/platform/offline-worker.test.ts` adds the first visit end to end (the install fails as the deploy lands, the page reloads, the new build installs whole and opens offline: it failed before with 0 reloads) and the returning visit (the last whole cache stays in charge; it held before too). `src/platform/offline.test.ts` covers `watchInstall` and `watchFetches` (it drops #584's `reloadOnStaleChunk` cases, now in the stale-build tests); `src/app/states.test.ts` covers `reloadLosesNothing`. The offline browser spec adds two cases: a deploy during the install while the bot races (no reload over 600 more sim ticks, one reload on quitting to the menu, then a whole cache and an offline race) and San Francisco's map files answering 404 at the menu (one reload, remembered).
- **Budget**: first-load JavaScript 482,514 to 483,489 bytes gzip (+975) of 512,000, so 28,511 headroom, from a local `vite build` of each (main's four changed sources against this branch's; measured as `scripts/perf.mjs` does).
- **Not covered**: a first visit that goes offline before it could reload has no whole cache to open; an install that fails with no deploy still waits for the next launch.
