The perf check now times the start tap. It reports the tap's main-thread work (its click handlers, then the next frame's work) as a trend with the same 3x guard as frame time. Before, nothing on CI measured the start tap. No game code changed.

Why: polish F's live check timed the menu after the start tap. It took a median of 215 ms on builds before 2026-10-06's afternoon render and content PRs (4 runs, at most 251) and 461 ms after (5 runs, at least 327). The check could not say why. Here is what this lane measured without a browser, on main (c2afc12) and on 303351b (the build before that span):
- The tap's own code did not change. Between 303351b and 00d41c9, git shows no change under `src/app`, `src/ui`, `src/audio`, `src/platform` or `src/main.ts`. On a fake audio context, the tap's audio graph build takes 0.05 ms of JavaScript.
- The menu's backdrop does the same work on both trees. For the Keys' `keys-m1` road, `stillSceneOf` builds 23 parts, 353 draws and 170,010 triangles on both. Its build time in Node was 412 to 481 ms on 303351b and 400 to 665 ms on main, three runs each on a shared machine. Baking its 10 model kinds takes 24 ms on main and 29 ms on 303351b.
- The content work after boot got cheaper with #626. Building the base registry when the Keys' real roads arrive takes 12.9 ms with the pre-parsed copy, against 19.5 ms with Zod. The boot base registry takes 6.6 ms, against 10.9 ms. The shipped real-road files are the same size (849,378 bytes). The content hash at that moment (70.6 ms) is unchanged code.
- In every "after" run of the live check, the tap came as the models, the roadside and text-surfaces chunks or the dev chunk were still arriving (within 150 ms of the tap). The one "before" run with long-task data (303351b) tapped 2 s after the first screen, when that loading had ended.

So no change in the span grew the work between the tap and the next frame by anything these checks can see. The live difference is not attributed to a change, and nothing is cut here. A cut without a measured cause would be a guess. This probe gives the next change a number on every PR.

How it measures (`tests/perf/perf.spec.ts`): before the tap, the page adds a capture listener for `click` on window (it runs before the start screen's own handler) and a bubble listener (it runs after). The bubble listener queues a frame callback. That callback runs after the game loop's own callback, which was queued a frame earlier, and records the time from the frame's start. The test waits for the menu and for that callback, never for a duration. The probe prints a `perf start tap` line and writes the parts to the probe's JSON. `judgeSoft` adds a `start tap` row once `soft.startTapMs` exists in `tests/perf/baseline.json`: the value, its ratio and a 3x guard with no frame slack (`scripts/perf-limits.mjs`). `scripts/perf-limits.test.ts` covers that row. It shows the row firing just above 3x, failing on a missing reading, and staying out until both the probe and the baseline have it (the negative control). The baseline is CI's own reading (this PR's runs), not a local number. Docs updated: `docs/engineering.md` (perf check, soft tier). Not phone-verified (no game change).
