A rider or bike model the game server held back now arrives in the same race once the wait is over, instead of only at the next race. The last live check found that a Keys race started inside San Francisco's 30 second wait kept Deacon Vane and the chopper as plain stand-ins for the whole race (a race lasts several minutes; the wait ended about 30 seconds in). Now the game asks for each held model once, just after the wait passes, and swaps it in while you ride. A model the server does not have (a 404) is still not asked for again, and a server that keeps asking for waits is chased at most three times in a row.

For devs: the manifest (`createAssetManifest`, `src/assets/index.ts`) reads the wait from a held answer's `Retry-After` (the loader's own hold answers 429 with the wait that is left), sets one timer for it (`later` option, the clock's by default; waits over 5 minutes, a `Retry-After` of 0 or one that cannot be read set none), and calls the listeners of the new `onRetryReady(listener)` with the id when the timer fires, only if the id has not loaded or started loading by then. It stops after `WAIT_ASKS_MAX` (3) such calls in a row for one id; a load resets the count. `RiderRigs` (`src/render/riders/index.ts`) listens and asks again for any part it holds as `retryable`. A rig built on the starter bike because its own bike was held back is rebuilt on the real bike when it arrives (`Rig.bikeStandIn`), and a rig built or rebuilt for a part that arrived late is limited to `LATE_RIGS_PER_FRAME` (1) a frame, so models that arrive together never cost a frame-time spike; the rig is made in the next frame's `update`, after the answer came in between frames. Scenery models (`requestModels` in `src/render/index.ts`) are not swapped mid-race: that needs a road rebuild, which is a hitch; they are still asked for at the next road.

Polish L punch item 3: each failed model answer was followed about 10 ms later by a `net::ERR_ABORTED` for the same file in the network record. It was only noise, from #666's `res.body?.cancel()` on a failed model answer in the manifest; that cancel is gone (the small error body is left unread). The cancel on answers the loader drops before a retry (`retryingFetch`) stays as #614 made it. Not checked in a browser.

Tests: `src/assets/after-wait.test.ts` (the timer and the listeners, with controls for a 404, a 503 with no wait, a lost connection, a wait of 0, a wait over 5 minutes, an unreadable wait, a model that loaded first, and the cap of 3; the body of a failed answer is not cancelled, which fails with the cancel put back), `src/app/model-after-wait.test.ts` (the real `retryingFetch` and manifest over a scripted host: the held model arrives after the wait with no second race; with no listener, as on main, the stand-in stays until the next load; a 404 sets no timer and is asked once), `src/render/riders/after-wait.test.ts` (rig swap on the rider, on the bike, one late rig a frame, and no ask for a model that is gone). Not phone-verified, and not checked against the live host.
