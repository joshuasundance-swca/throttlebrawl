The first-load JavaScript has 50.6 KB of headroom again, up from 12.7 KB. It is 449.4 KB gzip of the 500 KB budget, down from 487.3 KB on main (eaa8f25). The sim's step now loads after the first screen. Each system (riders, AI, combat, cops, traffic, pedestrians, crashes, race, event modifiers) keeps its state, its init, its tuning and what a snapshot reads in its `index.ts`. Its step, and the code only the step reaches, moved unchanged to `src/sim/<system>/step.ts`. The law's props, the shortcut stamps, the crash rig and its contacts, and the run back moved with them. `src/sim/steps.ts` gathers the steps into one lazy chunk, `sim-steps` (43.4 KB gzip). The app loads it in the background at boot, together with the structures' planners. A race already waited for the planners, and now it waits for both. The menu's grid is a sim that is made and snapshotted but never stepped, so it needs none of this code. A sim stepped before the chunk has loaded throws. It never steps with a rule missing. No feature was dropped and no rule changed. The build's self-test race (3,600 ticks, the whole field on the AI, drafts included) hashes `74c1c590` before and after. The sim's code hash covers the new chunk, as it covers the planners' chunk, so the replay key still changes when the step changes.

Why: on 2026-10-07 the headroom fell from 26.6 KB (01ed22c) to 17.3 KB (ee66ddd) in one morning, then to 12.7 KB on main. The next feature PRs would have hit the 10 KB floor. I built each first-parent commit from 01ed22c to eaa8f25 (19 builds) and measured each one's first load. Most of the growth was sim code: #663 +4.0 KB (structures are solid), #672 +2.7 KB (the course's edges), #657 +1.5 KB (set-piece props are physical), #676 +0.8 KB (the law's props). #677 added +2.9 KB to the main chunk (the camera on a roof). About 55% of the eight split systems' source (350,493 of 636,009 bytes, comments included) is code that only a running race runs. Moving it was the biggest cut available that does not delay the first race. That race already waited for a lazy chunk, the planners, which loads at the same moment as the steps.

What else changed: `loadSimSteps` is a new, additive export of `src/sim/api.ts`. It rides in this PR instead of landing first as its own contract PR, because nothing else uses it. `scripts/sim-chunk.mjs` gains `SIM_STEPS_TEST` and a third chunk group. The sim group leaves those files out, because a group takes its modules' dependencies with it, so putting the steps' group first would pull the whole sim into it. The tests' setup (`tests/setup/structures.ts`), the build's self-test (`scripts/selftest-race.ts`, with a top-level await, because Vite's module runner closes once the import returns), `?selftest=1` and the test flag's handle (`src/main.ts`, before `botAttackRuns` can run) all load the chunk first.

Tests (failing first): `src/app/late-steps.test.ts` makes and snapshots all 102 grids (51 events, 2 seeds each) in a fresh module graph without the chunk. As its negative control, the same sim throws on `step` until the chunk loads, and once loaded it hashes the same as the setup's sim after 600 ticks. Before the move it failed because the sim stepped without the chunk. `scripts/first-load.test.ts` lists the step files and their helpers as lazy. It caught a `tumble/rig.ts` that an `import { type Cluster }` had kept in the first load. `scripts/sim-chunk.test.ts` checks that a change to `src/sim/ai/step.ts` lands in the lazy chunk, which the sim chunk only imports dynamically, and that the change moves the code hash. Docs: architecture.md ("The step loads late", under the sim contract) and engineering.md (the first-load list). Not phone-verified. A phone should show the menu a little sooner on a slow connection, because the first screen downloads 37.9 KB less before it appears.
