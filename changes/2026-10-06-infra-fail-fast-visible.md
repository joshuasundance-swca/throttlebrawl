A red PR run now says which job failed and which tests, right on its `gate` (or `quick`) check. Since fail fast arrived (#557), the red job cancels its own run, so it ends "cancelled" like every job it stopped, `gh run view --log-failed` printed only the gate's log, and the gate said only "suite is cancelled". Now the cancel step first leaves an error annotation naming its job, and a red gate reads the run's jobs and the red job's log (`node scripts/train.mjs failures`, with a read-only `actions: read` token) and names the red job, its failed step and its failing tests in its log, its summary and its annotations: `gh run view <run>` lists them, and `gh run view <run> --log-failed` prints them (the naming step fails on purpose, since that command prints only failed steps). A red gate with no failed step says so and names the jobs a cancel cut short (a timeout ends a job cancelled too); on a push to main, where nothing fails fast, a slice that timed out is named beside the red one. Fail fast still frees the runners at once: the annotation is one `echo` before the cancel, and the naming runs in the gate only after a red verdict, so it cannot change its colour. The bundle train's own report uses the same red-job rule. Checked by running the new command against this repo's real red runs: PR runs 37417692149 (a unit slice) and 37412561136 (a sim slice), where it named the job and the failing test, and main run 37418801318, where it named browser 2/7's failed build and browser 5/7's timeout. Not phone-verified (no game change).
