A lane that needs another lane's unmerged work no longer sits idle until that work merges (the maintainer, 2026-10-06, after asking "did we consider stacked PRs": "Proceed as recommended without gh stack at this time."). It branches from the parent's pushed branch, builds and tests there, and opens its PR against `main` only after the parent's PR is MERGED, merging `origin/main` in first (never a rebase, never a force-push). It makes its branch with `git switch --no-track` and pushes it with `git push -u origin HEAD`, so it can never push onto the parent's PR, and it stops waiting 8 hours after its branch was ready, with the branch pushed and the parent reported blocked. It never opens a PR against another lane's branch: that gets no CI and no train, and auto-merge there would merge at once with no checks. GitHub's `gh stack` extension was considered and deferred (its cascade rebase and force-push conflict with the never-rebase rule, CI and the train only see PRs into `main`, and its merge lands the whole stack at once, directly or through GitHub's merge queue, never through the train); revisit if the repo adopts the merge queue.

For devs: the rule is one bullet in `AGENTS.md` ("Runs: lanes, one keeper, one live check") and a subsection in `docs/engineering.md` ("Lanes that build on another lane") with the reasons. `.claude/workflows/lane-run.js` takes an optional `needs: <lane key>` per lane: that lane starts when its parent lane has finished (before taking a pool slot), is told to build on the parent's PR head branch and to open its own PR only after the parent merged, and a missing key, itself or a cycle is refused at the start. `scripts/stack-lite-docs.test.ts` pins the three statements of the rule, reads each reason back against `ci.yml` and `scripts/train.mjs`, and finds a planted fault in each checker. `CONTRIBUTING.md` does not tell contributors about dependent branches (it says to branch from `main`), so it is unchanged.
