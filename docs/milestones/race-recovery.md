# Race recovery after a reload

`[default]` Provide the decided M2 recording-based resume in career and Quick Play. Use the existing replay controller, synchronous storage and [recovery-card contract](./race-recovery-card.md). Keep replay and profile schemas unchanged, with no sim snapshots, new dependencies or acceptance infrastructure.

## Saved attempt

APP owns one atomic `saved-race` version 1 envelope at the existing `<appId>:race` key. It carries the encoded recording, APP logic version, original context, exact saved-state hash and phase. `riding` has no end marker; `pending-result` has an end marker at the last stepped input plus frozen result build/time. Legacy raw recordings have unknown context and are retained with a plain notice, never restored as assumed Quick Play.

Quick context preserves its qualified event, original route and complete retry settings. Career context preserves the qualified career definition key, node/event association, original length and exact supported persisted profile record. Derive the frozen starting profile from that record. Compare a fresh actual storage read before reconstruction and award; a failed profile write's memory cannot authorize a disk match. Always settle a retry from the frozen starting profile and frozen terminal metadata, replacing the in-memory result rather than adding another award. Save the profile successfully before clearing the attempt. A successful award followed by failed clear leaves a changed-profile attempt that refuses safely. This is a conservative single-tab contract, not transactional settlement across concurrent tabs.

Keep APP logic compatibility separate from simulation compatibility. The replay key covers physical code and event content, but excludes career files. Compare an APP canonical derived-data identity covering selected definition/node/plan, season setup, chosen ask/gig, recorded ridden bike plus its repair price, and grant-associated bike availability. Quick Play includes its event plan, original route and complete retry settings, using the same identity function at capture and restore. Resolve the qualified career against all carried non-road metadata; load only the recorded event's actual road closure and planners. All career shop metadata is already carried at boot, so repair pricing uses the same complete set as ordinary settlement. Presentation-only code updates need not invalidate recovery.

Validate the complete text before JSON parsing and run expansion. Default limits are 2,097,152 characters including context/profile and 216,000 stepped ticks (one hour at 60 Hz), with the current one external player slot. These are resource limits, not gameplay duration or storage-quota guarantees. The complete unit fixtures measure 945,738 characters for six minutes of changing steering and 651,042 for fifteen minutes of constant input. They include the actual derived career identity, 200 synthetic history entries and three synthetic 190,000-character backup codes accepted by the profile sanitizer; they are not recordings of completed careers or real exported backup codes. Reject malformed counts, unsafe sums, invalid quantized values, unsupported versions, out-of-range params/hashes, phase/end disagreement and inconsistent header/config/context identity before decoding. Retain refused input. Maximum decoded allocation and phone storage remain unverified.

## Runtime ownership and choices

Save every 300 stepped ticks and synchronously on pause/hide. Only the matching ordinary race instance and attempt token can save; menu intent generations are not a substitute, because pausing itself may advance them. Countdown, attract, measurement and replay-viewer activity never save or settle an ordinary attempt. Explicit restart/abandon retires that owner. Retain a failed result save until retry or explicit abandonment; it cannot be overwritten by another ordinary race.

Quitting is explicit abandonment of the recoverable race, followed by the ordinary quit policy. A failed quit-profile write is reported as memory-only; it is outside completed-result recovery. A countdown with no stepped input is never saved as a resumable race. Only persist a riding phase after the step's result decision, so a periodic save cannot publish a terminal tick as unfinished.

A failed initial storage read leaves the slot unknown. Keep the menu usable with race-slot writes disabled and a truthful notice until a successful read classifies it. Never treat unknown as empty. Classification never deletes legacy, newer, malformed, stale or incompatible data. Explicit Start over authorizes forgetting it; failed removal is reported honestly.

Classify a known saved attempt before the ordinary pointer/keyboard Start path can open the menu. Either recovery-card choice activates platform/audio synchronously before awaiting. Missing content offers Retry/Start over; incompatibility or desync retains evidence and offers Start over without Resume. Every failure clears busy state and restores a usable choice. An unfinished recovery lands paused with countdown complete. A pending result checks its terminal hash and recovers results without another gameplay tick or `recorder.resume()` dropping the end marker.

Rebuild historical outcome, objective log, onboarding and producer ask on every recorded step in ordinary order, using the pre-step tick and post-step snapshot. Include events on the tick that creates the ask. Preserve early completion and its delayed-results beat. Historical folding has no audio, ticker, haptic, veto or UI side effects. Continue recording only for unfinished attempts. Use the existing optional DEV resume-report seam for saved/refused key, tick and measured fast-forward; do not add another monitoring tool.

## Automated acceptance

1. Atomic recording/context/hash roundtrip; both phases; healthy empty-slot positive; legacy/newer/stale/malformed refusal with original evidence retained; blocked read, quota/write and removal failure controls. Unknown slots and pending results cannot be silently overwritten.
2. Pre-parse character bound and pre-expansion run/tick/input/header/phase validation, with an accepted bounded recording as the positive control. Print the actual complete encoded sizes of the representative long/profile fixtures.
3. Original versus reconstructed sim hash at the saved tick and later ticks, non-default config/tuning and actual regional roads preserved after menu changes. Tampered checkpoint and final saved-state hash refuse.
4. Career node/season, objective status/tally, onboarding and ask match an uninterrupted control. Cover ask creation and fulfillment on the same threshold tick, an objective ending early, and pre-step delayed-results boundaries. No historical presentation effects; Quick Play never settles career rewards.
5. Failed award retry replaces the same frozen output; successful profile save followed by failed clear cannot pay twice. Profile import/change, rule-data change and ambiguous bare-region controls refuse or resolve the original qualified definition correctly. Pending-result recovery checks end/hash without another sim step.
6. Actual browser fresh profile → selected race → deterministic ticks → pause/hide synchronous save → reload → real offer → Resume → paused at original tick → continued hashes matching control. Cover original options/retry, Start over, stale input, pointer/keyboard precedence, failed content retry and visible error states.
7. Measurement leaves ordinary recording/profile/settings/envelope unchanged and offers no diagnostic save or recovery. A completed ordinary race's stale in-memory recorder cannot be flushed by measurement lifecycle events.
8. Normal named units/authored sim files, hooks, types and full CI; one coordinated served recovery check with rendered card and paused race. Keep budgets and phone headroom. Phone OS reopening, native installation, arbitrary long sessions and concurrent-tab settlement remain unverified.

Completion means the actual APP flow and its acceptance pass, not the card or storage helper alone.
